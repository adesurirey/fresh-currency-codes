# v1 stability contract covers the API and data shape, not data values

At `1.0.0` we commit to semver. For a library whose code is frozen but whose dataset is refreshed automatically every week, "stable" needs an explicit boundary: **the 1.x contract covers the public API surface and the `CurrencyCodeRecord` data shape — not the data values.** Currency additions, deprecations, and country/digit corrections are expected churn, not breaking changes. Freshness is the entire point of the fork (see [ADR-0007](./0007-auto-publish-on-version-bump-merge.md)); consumers opt into a *living dataset*, and anyone needing a frozen snapshot pins an exact version rather than a range.

Consequently the weekly refresh stays uniformly `npm version patch` with no bump-level logic — deprecations included. A deprecation flips a currency to `active: false` and removes it from default lookups, but the record is preserved (ADR-0005), reachable via `{ includeDeprecated: true }`, and bounded by the sanity guards (≥100 active, ≤10 removals/run). It is a data-value event, not a contract event. Special-casing it as `minor` would add fragility to the highest-value automation and leak the data-vs-contract distinction into the pipeline.

A `2.0.0` is reserved for human-gated contract changes only: removing/renaming a public function or a `CurrencyCodeRecord` field, changing a field's type (e.g. `number` back to a JS number, collapsing `digits: null` into `0`), changing the country-name format (ADR-0004) or the `includeDeprecated` default, or dropping a supported Node major or the ESM-only artifact shape (ADR-0008).

The safety property that makes "v1 + fully automated weekly publishing" sound: **the automation can only ever mutate data values.** The output shape is hard-coded in the ingest script, not derived from the upstream XML — if SIX-Group adds or renames fields the ingest ignores them, and if it removes a field the ingest depends on the affected entries are dropped and the G2 guard aborts the refresh rather than publishing a malformed dataset. The API + data-shape contract can change only through a human PR, which carries the appropriate minor or major bump. There is no automated path to a breaking change.
